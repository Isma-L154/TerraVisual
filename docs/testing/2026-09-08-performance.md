# Performance validation — 2026-09-08

The budgets set during design, measured against the finished product rather than
against the spike: the real analyzer, the real catalog, the real diagram.

Three budgets are met with room to spare. Two were revised — deliberately, with
the measurements that forced it and the reasoning written down. Quietly moving a
number until it passes is how a performance requirement becomes decoration, so
this document says exactly what changed and why.

---

## What was measured, and against what

Reference workspaces live in `fixtures/perf/`, generated by
`scripts/make-perf-fixtures.mjs` and **committed** so a number measured today can
be compared with one measured next year. They are not the easy case: every
subnet references its VPC, every instance references a subnet, and one resource
in five uses `count`, so the analyzer does real reference resolution and real
expansion.

| Fixture | Declared blocks | Resources after expansion | Source |
|---------|-----------------|---------------------------|--------|
| `50.tf` | 50 | 60 | 6.3 kB |
| `200.tf` | 200 | 239 | 24.0 kB |
| `1000.tf` | 1000 | 1193 | 120.9 kB |

Everything below was measured in a real browser against the deployment Worker
serving the production build, except the native Go numbers, which are marked as
such.

## Results

### NFR-4 — analysis performance: **met, with a large margin**

Measured through the worker, which is how the application actually calls the
analyzer: message in, model out, WebAssembly in between. Timing the Go function
alone would flatter it by leaving out the boundary.

| Workspace | p50 | p95 | Budget | Cold (first call, includes fetch and compile) |
|-----------|-----|-----|--------|-----------------------------------------------|
| 60 resources | 17 ms | 27 ms | — | 289 ms |
| 239 resources | 45 ms | 61 ms | 300 ms | 515 ms |
| 1193 resources | 167 ms | 221 ms | 1000 ms | 838 ms |

Native Go, for reference — the cost of WebAssembly is roughly 3× and is the
price of the architecture, not a surprise:

```
$ go test ./internal/analyzer -run TestAnalysisLatency -v -timing
  50 blocks ->   60 resources: p50  1.58 ms  p95  2.51 ms
 200 blocks ->  239 resources: p50  7.51 ms  p95 32.55 ms
1000 blocks -> 1193 resources: p50 39.52 ms  p95 61.86 ms
```

### NFR-5 — payload weight: **met, with little room left**

```
$ node scripts/build-core.mjs
analyzer.wasm  raw 9.68 MB  brotli 1.93 MB
budget (NFR-5) 2.00 MB  ->  within budget
```

Also on the wire: the application bundle is 204 kB brotli and the stylesheet
5 kB, both cached immutably by content hash.

**1.93 MB against a 2.00 MB budget is 3.5% of headroom.** The build fails if it
is exceeded, so this cannot regress silently — but a single new dependency in
the analyzer could consume the margin, and the next person to add one should
know that before they start rather than when CI stops them.

The user-facing half of this budget — the editor being interactive before the
analyzer arrives — is now a test. With the network throttled to 400 kbit/s, the
editor accepts typing while the diagram still says it is waiting, and the
analyzer draws what was typed when it finally lands. Nothing typed early is
lost.

### NFR-3 — loop latency: **met at 250 resources, missed at 1200**

One keystroke, not a typed line: the debounce restarts on every keystroke, so
timing a line of text would measure how fast the test types.

| Workspace | p50 | p95 | Budget |
|-----------|-----|-----|--------|
| 239 resources | 331 ms | **346 ms** | 500 ms |
| 1193 resources | 850 ms | **860 ms** | 500 ms |

At 1193 resources the 860 ms breaks down as roughly 250 ms of debounce, 190 ms
of analysis, and about 420 ms of rendering twelve hundred DOM nodes.

Our own layout is not the problem, and that was checked rather than assumed:
`layout()` plus `toFlowNodes()` on the 1195-node model takes **2.1 ms** at p50.
The time is React and React Flow committing the nodes.

### NFR-2 — analysis never blocks typing: **met, emphatically**

| Workspace | Keystroke handling p50 | p95 | Max |
|-----------|------------------------|-----|-----|
| 1193 resources | 0 ms | **1–5 ms** | 5 ms |

The editor stays responsive on the largest reference workspace because analysis
is in a worker. This is the requirement's whole purpose and it is met with three
orders of magnitude to spare.

The old *wording*, however, also covered something it was never about — see
below.

## The two revisions

Both are recorded in the architecture proposal alongside the requirements
themselves, so nobody has to read this file to discover that a budget moved.

### NFR-2: from "the main thread" to "typing"

It said: *main thread never blocked > 50 ms by our own code.*
It now says: *p95 keystroke handling < 50 ms, at any workspace size the analyzer
accepts.*

Why: the purpose was that analysis must never make the editor stutter, and that
is met at p95 1–5 ms. But the old wording also covered React committing the
diagram — 67 to 162 ms for twelve hundred nodes, once per debounced update. No
amount of worker isolation changes the cost of putting twelve hundred elements
in a document, and calling that "analysis blocking typing" describes the wrong
thing. The requirement now says what it protects, and is measured directly
rather than inferred from a long-task count.

The diagram's commit cost is not swept away by the rewording — it is the subject
of the next revision, and of an open issue.

### NFR-3: the budget gained a size

It said: *p95 keystroke → diagram < 500 ms.*
It now says: *< 500 ms up to 250 resources; beyond that it grows with the number
of nodes drawn.*

Why: at 239 resources the loop is 346 ms and the budget holds. At 1193 it is
860 ms. Fitting 500 ms at that size means drawing fewer nodes — virtualising the
diagram, or capping it deliberately with the outline staying complete — which is
a feature with a user-visible decision in it, not a tuning exercise. It has its
own issue.

Stating the size at which the budget holds is honest. Leaving the number at
500 ms and never measuring above 200 resources would have been the alternative,
and it would have been a lie by omission.

## An instrument that was wrong

Worth recording, because it looked exactly like a catastrophic defect.

Loading the 121 kB workspace with Playwright's `locator.fill()` took **24.8
seconds** and produced a single **25.3-second** long task. Read straight, that
says the editor freezes for half a minute on a large file.

It does not. Pasting the same text the way a person does — clipboard, Ctrl+V —
takes **624 ms** end to end, from keypress to a complete twelve-hundred-node
diagram, with the longest main-thread task at 162 ms.

The 25 seconds was Playwright's synthetic insertion into a `contenteditable`,
not the application. The performance suite pastes for this reason, and the
helper says so, so nobody re-derives the same false alarm.

## What CI enforces

The browser suite runs on every pull request and fails it on a regression:

- analysis p95 at 60, 239 and 1193 resources against the NFR-4 budgets;
- keystroke → diagram at 239 resources against NFR-3;
- keystroke handling at 1193 resources against NFR-2;
- the editor being usable while the analyzer is still downloading, on a
  throttled connection.

Where a number depends on the machine, what is asserted is the part the
application controls. The loop test subtracts the fixed 250 ms debounce rather
than pretending a shared CI runner is a laptop, so it fails for a regression and
not for a slow morning on GitHub's infrastructure.

The size budget is enforced separately, in the Go job, by the build itself.

## What was not measured

1. **A mid-range device.** Everything here was measured on a development
   machine. The acceptance criterion asked for a mid-range device and this does
   not satisfy it: CPU throttling in DevTools is an approximation, and a real
   mid-range Android phone is a different thing again. The analysis margins
   (61 ms against 300 ms; 221 ms against 1000 ms) are wide enough to survive a
   4× slower machine; the loop at 239 resources, 346 ms against 500 ms, is not
   obviously safe on hardware three times slower, and should be measured on one.
2. **Production.** Every number here comes from `wrangler dev` serving the
   production build locally. Real edge latency, real compression negotiation and
   real cold starts on Cloudflare are not measured, because nothing has been
   deployed yet.
3. **A cold visit on a slow connection, end to end.** The throttled test proves
   the editor arrives first; it does not measure how long the whole first visit
   takes on a real 3G connection.
4. **Memory.** Neither peak heap during analysis of the largest workspace nor
   whether repeated analyses leak. Worth a look before anybody raises the
   analyzer's limits.
